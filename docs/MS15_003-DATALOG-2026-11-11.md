# MS15_003 TunerStudio binary datalog review — 2026-11-11

**Status: owner-supplied telemetry examined; no source edits, new build, firmware flashing, physical I/O measurement, or firmware release.** These observations establish what the MLG file reports; they do **not** independently establish the actual ECU's flash contents, electrical outputs or engine behavior.

## Input and parsing

User uploaded TunerStudio `2026-11-11_15.57.31.mlg` (30,360 bytes). This is an `MLVLG` version 2 binary log: 34 self-described channels, 82 bytes of field payload per record, five bytes of record framing, 312 consecutive records (312 × 87 = 27,144 bytes) beginning at offset 3216. Header's capture description identifies **TunerStudio MS Lite 3.3.01**, `Wed Nov 11 15:57:32 EST 2026`; header's firmware-definition text is **`MS1/Extra format MS15_003 ******`**. The embedded signature documents the logging definition; it is not an independent readback of the ECU flash.

Samples span `Time=0.000` to `20.661` seconds. Record counters increase by one modulo 256 for every consecutive block (311/311 transitions). This shows no missing *record sequence numbers*, not proof of error-free serial communication. The file does not directly expose the TunerStudio user-interface Protocol Error status.

## Measured values

- `RPM` approximately 289–1,776. The trace begins near 750 RPM, drops around 300, then stabilizes near 1,775 RPM after 9.3 seconds. This pattern is consistent with a Stim session, but the uploaded file alone does not establish what hardware generated the signal.
- Both `PW` and `PW2` report nonzero injector pulse widths, predominantly 10.5–11.5 ms; maximum 20.9 ms during an acceleration-enrichment event. These are ECU-calculated/reported values; actual injector waveforms weren't measured.
- `MAP` stays at 94; `batt V` stays near 12.12 V.
- `CLT` is mostly 50 followed by 68, with a brief excursion up to 228 at 11.129 seconds. This cannot be interpreted as a physical engine temperature change without context; a Stim-pot adjustment is one possible cause.
- `Gwarm` is exactly 100% in all 312 records. No warmup (Engine bit 3 / 0x08) is recorded.
- `TPSacc` increases temporarily and Engine bit 4 (`TPSAEN`, 0x10) is present in five samples. Engine bit 5 (0x20, TPS deceleration) appears in nine samples.
- `idleDC` reports zero throughout, but this is not an independent stepper-IAC motion/position measurement. The `Spark Angle` column remains -10, an inherited telemetry field not proof of an ignition function.

## Logged front LED GPIO states

The source firmware maps LED17 to Port C bit0 (mask 0x01), LED18 to Port C bit2 (mask 0x04), and LED19 to Port C bit1 (mask 0x02). The log contains `portc` values 8, 9, 10 and 11.

- **LED17 / Squirt:** Port C bit0 high in 73 of 312 samples with 21 observed rising transitions. Port A high injector-driver bits (0xC0) are present in 73 samples, 61 simultaneous with Port C bit0 high. Sampled data cannot establish precise edge overlap at ~15 Hz.
- **LED18 / WUE:** Port C bit2 never high, consistent with `Gwarm=100` and WUE engine flag always zero.
- **LED19 / Accel:** Port C bit1 high in two samples at 15.395 and 16.595 seconds, and in both the TPS acceleration bit is set. Five total samples show the TPS acceleration bit; the LED service polls at ~100 ms and cannot be checked for perfect sub-sample timing here.

**Interpretation:** Logged GPIO states support that the native LED modes are active as intended. Actual LED circuitry, injector edge timing, IAC/relay operation, and stability under real engine loads remain unverified. No 'protocol error' conclusion can be drawn from the absent UI-only indicator in this binary log.
